# pr-review CLI

The deterministic backend behind `/pr-review`. Reviews GitHub PRs end to end
— real type-check/lint/test runs, real before/after screenshots, a rendered
HTML dashboard and a paste-ready markdown comment — without ever posting to
GitHub or touching the live working tree.

This file is the canonical spec: exact CLI commands, the capture-plan JSON
shape, size tiers, and quality-gate rules. Every module in this folder is
built against what's written here, so keep this file and the code in sync
when either changes.

## Why this exists: the three-layer split

```
/pr-review command (orchestrator)  →  pr-reviewer agent (per PR, judgment)  →  cli.mjs (mechanical work)
```

The load-bearing rule: **the model only ever writes judgment; this CLI does
everything mechanical and everything that has to come out byte-identical
across runs.**

- The orchestrator command never reads code or reports — it only calls
  `prepare`, launches one `pr-reviewer` agent per PR, and prints a table from
  the agents' one-line returns.
- Each `pr-reviewer` agent reviews exactly one PR and writes exactly one
  file — `review.json` (decision, findings, lens verdicts). It never
  hand-writes `findings.json`, HTML, or markdown.
- This CLI does the rest: git plumbing, diffing, running checks, route
  detection, screenshot capture/diffing, and assembling + validating +
  rendering the final report. Deterministic, and covered by
  `test/*.check.mjs`.

That split is why two runs of the same PR at the same head produce the same
report shape — the model's only degrees of freedom are the judgment fields
in `review.json`; everything else is generated by code from a schema.

## Prerequisites

Claude Code plugins never run install scripts, so this one-time setup is
manual, in `pr-review/`:

```bash
npm install
npx playwright install chromium
```

`npm install` pulls this folder's only two real dependencies —
`playwright` and `typescript` — declared in `pr-review/package.json`.
`npx playwright install chromium` then downloads the actual browser build
Playwright drives. Skip both entirely if you'll never run `/pr-review`;
every other command in this plugin works without them.

## Commands

Dispatch: `node cli.mjs <command> --flag value ...`. Every command prints
JSON to stdout unless a flag says otherwise.

### `prepare`

Run once, by the orchestrator, before any agent launches.

```
node cli.mjs prepare --prs "670 671" [--force] [--no-screenshots]
```

- Fetches each PR's refs via git, resolves its base SHA, merge SHA, and base
  branch (the PR's actual merge-base — **never** `main` directly, since
  `main` may have moved since the branch point).
- Skips a PR already reviewed at the same head, unless `--force`.
- Allocates a pair of dev-server ports per PR (`PORT_BASE`, `PORT_HEAD`).
- Emits `{ launch: [{ PR, prompt, ... }], skipped: [{ pr, reason }] }` — each
  `launch` entry's `prompt` is the fully-formed prompt string the orchestrator
  passes straight through to a `pr-reviewer` agent, with every `KEY=value`
  input (see `agents/pr-reviewer.md`) already filled in.
- All git/network plumbing for orchestration lives here, deliberately kept
  out of any subagent's token budget.

### `triage --repo <path> --from <sha> --to <sha> --out <path>`

Classifies every changed file — generated / test / doc / style / config /
source — and excludes noise (lockfiles, snapshots, whitespace-only diffs,
pure renames) from the "reviewable" line count. See **Size tiers** below for
how the result buckets the PR and picks which units get a full read.

Prints a 5-line console summary (tier, deep vs. skimmed unit counts,
exclusions, changed-file count) and writes the full detail to `--out`.

### `checkout --repo <path> --ref <sha> --dir <path>`

`git worktree add --detach <dir> <ref>` — deliberately not the native
worktree tool, since PR review needs to check out arbitrary refs (a merge
SHA, a base SHA), not just branch off current HEAD. `node_modules` is
**symlinked** in, never copied; `.env`/`.env.local` are copied.

### `dispose --repo <path> --dir <path>`

Reverses `checkout`: unlinks the `node_modules` symlink **before** removing
the worktree directory — this ordering matters, so a botched or partial
removal can never chase the symlink into the real `node_modules` — then
`git worktree prune`.

### `refs-delete --repo <path> --pr <n>`

Deletes the PR refs `prepare` fetched. Always run during cleanup, even on
failure.

### `checks --head <dir> --base <dir> --files <comma-list> > <path>`

Runs, in the background, against the changed-file list only (never the
whole repo):

- **Typecheck** — never a raw `tsc -b` call; wrapped so it can't hang or
  blow up the agent's context with raw compiler output.
- **Lint** — ESLint against the changed files only, diffed against base.
- **Tests** — the full test suite.

Each parsed down to a compact `{errors, sample}` row — the agent consuming
this never sees raw tool output.

### `diff --repo <path> --from <sha> --to <sha> --unit <unit> [--max <n>]`

A compact unified diff, 2 lines of context, reviewable files only, for one
triage "unit" (roughly: a file-path group). `--max <n>` caps output lines
for a "skimmed" unit rather than a "deep" one.

### `routes --repo <dir> --files <comma-list>`

Statically walks the TS/TSX import graph from the changed files (via the
TypeScript compiler API) to find every route path that could be affected.
If a changed file is import-reachable from effectively everywhere (an app
shell, a global stylesheet, `main.tsx`) it's flagged as a **global** change
instead of an enumerated route list.

### `sweep --routes <path> --max <n> > <path>`

Given the `routes` output, produces up to `<n>` sweep scenarios (page-load
screenshots, no interaction) — the baseline coverage layer that
interaction-specific scenarios (open a modal, submit a form) get added to
before capture.

### `serve --dir <path> --port <n>`

Boots a throwaway Vite dev server against a checked-out worktree on the
given port. The caller polls
`curl -s -o /dev/null -w '%{http_code}' <url>` (up to 60s) until it's ready,
then stops it after capture.

### `capture --plan <path> --base <url> --head <url> --out <dir> [--base-caption <str>] [--head-caption <str>]`

Runs the **capture plan** (schema below) against both running servers with
Playwright + Chromium:

- Freezes CSS animations before every shot.
- Uses a fixed `SUPER_ROLES` set of mocked roles/permissions broad enough to
  satisfy every route guard, so a capture never dead-ends on an
  authorization check.
- Shoots the **base** side twice first, specifically to measure a
  per-scenario noise floor (anti-aliasing jitter, font hinting) before
  comparing against head — this is what keeps sub-pixel rendering noise
  from being misreported as a real visual change.
- Classifies each scenario: `captured` (differs above the noise floor),
  `unchanged`, `new` (didn't exist on base), `failed` (a step errored), or
  `unreliable` (blank page, error boundary, redirected to a login screen).
- Writes `visual.json` (below) to `--out`.

Pixel comparison itself happens in `imgdiff.mjs`, done inside a Chromium
`<canvas>` — deliberately no native image-diff library dependency.

### `finish --repo <path> --pr <n> --repo-name <str> --head <sha> --merge <sha|none> --base <sha> --base-branch <str> --dir <path> --review <path> --triage <path> --checks <path> [--visual <path>]`

The only command that writes `report.html` / `report.md`:

1. Reads the agent-authored `review.json` plus the triage/checks/visual
   evidence JSON.
2. **Mechanically** assembles the full `findings.json` data model — every
   fact, verification row, and coverage percentage the agent didn't
   directly author.
3. Validates it against the schema (`schema.mjs`).
4. Renders both `report.html` and `report.md` from that one shared data
   model, so the two outputs can never disagree with each other.
5. Runs the **quality gate** (below) against the rendered HTML.

Exit codes: `0` success, `2`/`3` gate or schema failure — stdout lists
exactly what to fix. The calling agent may fix `review.json` and retry, up
to 3 times, but must never touch the template, CSS, schema, or the gate
itself.

## Capture-plan JSON

Written by the `pr-reviewer` agent (not this CLI) as the input to `capture`.

```json
{
  "scenarios": [
    {
      "name": "invoice-list-default",
      "route": "/invoices",
      "role": "Astra",
      "mocks": { "GET /api/v1/invoices": { "shape": "from src/services/invoices.api.ts" } },
      "base": { "route": "/invoices" },
      "head": { "route": "/invoices" },
      "steps": [
        { "type": "goto" },
        { "type": "waitFor", "selector": "[data-testid=invoice-table]" },
        { "type": "shot" }
      ]
    },
    {
      "name": "invoice-detail-modal-open",
      "route": "/invoices/123",
      "role": "Astra",
      "steps": [
        { "type": "goto" },
        { "type": "click", "selector": "[data-testid=open-detail]" },
        { "type": "waitFor", "selector": "[role=dialog]" },
        { "type": "shot" }
      ]
    }
  ]
}
```

- `name` — unique, becomes the screenshot filename stem.
- `route` — default path for both sides; override per side with `base`/
  `head` when the two checkouts should hit different text or state.
- `role` — which of the fixed `SUPER_ROLES` mocks to apply; omit for
  routes with no role gate.
- `mocks` — API response shapes, sourced **only** from the relevant
  `src/services/*.api.ts` module (never invented).
- `steps` — an ordered sequence, each one of:
  - `goto` — navigate to the scenario's route.
  - `click` / `fill` / `press` — interact with a selector.
  - `waitFor` — block until a selector appears (prefer this over any fixed
    delay).
  - `shot` — capture the screenshot; a scenario may shoot more than once
    (e.g. before and after opening a modal) by repeating `waitFor`/`shot`
    pairs.

`sweep`-generated scenarios are page-load only (`goto` → `waitFor` →
`shot`); anything with a `click`/`fill`/`press` step is agent-authored to
cover what the diff actually changed.

## Size tiers (`triage`)

| Tier | Reviewable lines | Behavior |
| --- | --- | --- |
| S | ≤ 400 | every unit read in full |
| M | ≤ 2,000 | every unit read in full |
| L | ≤ 10,000 | risk-ranked subset of units read in full ("deep"); the rest "skimmed" (capped diff) or "excluded" |
| XL | > 10,000 | same as L, plus the agent must set `decision: "Comment"`, cap `confidence` at 2, and say in `lede` that this can't be reviewed as one PR |

Risk ranking weights a file higher if its path matches the `SENSITIVE`
pattern (auth, security, permission, token, and similar) — these get
priority for a "deep" read even in a large PR where most units are only
skimmed.

## Visual output (`visual.json`)

Written by `capture`, read by `finish`:

```json
{
  "scenarios": [
    {
      "name": "invoice-list-default",
      "status": "captured",
      "basePath": "shots/invoice-list-default.base.png",
      "headPath": "shots/invoice-list-default.head.png",
      "noiseFloor": 0.004,
      "diffScore": 0.041
    }
  ],
  "tryIt": [
    "git fetch origin pull/<PR>/head:pr-<PR> && git checkout pr-<PR>",
    "pnpm dev",
    "open http://localhost:5173/invoices"
  ],
  "knownLimits": [
    "API responses are mocked from src/services/*.api.ts shapes, not live data.",
    "useUser() is stubbed — a PR touching src/hooks/useUser.ts cannot be verified visually."
  ]
}
```

`status` is one of `captured` / `unchanged` / `new` / `failed` /
`unreliable`. A `pr-reviewer` agent may downgrade a `captured`/`new` scenario
to `unreliable` by hand, with a note, if the after-image it viewed doesn't
actually show the intended UI.

## Quality gate (`quality-gate.mjs`, run by `finish`)

Loads the rendered `report.html` in headless Chromium and hard-fails
(`finish` exits 2/3) unless **all** of the following hold:

- No console errors.
- No horizontal scroll at either 1280px or 400px viewport width.
- Every image loads.
- Every internal reference resolves — `aria-labelledby`, `href="#…"`,
  `<use>`, `marker-end`.
- Nothing overflows its containing panel.
- Exactly one `<h1>`, and it has a `lang` attribute.
- The copy-to-clipboard button actually works.
- WCAG contrast passes for every color pair, in both light and dark theme.

This is a hard gate, not a lint suggestion — it's what keeps the report's
visual output stable release over release without a human proofreading each
one.

## Testing

```bash
node --test test/*.check.mjs
```

`fixtures/` holds `review.example.json` (the exact shape a `pr-reviewer`
agent's `review.json` must match) and other module-level fixtures.
`golden/` holds an approved-good rendered report for parity testing — a
module change that alters the golden output on an unrelated fixture PR is
almost always a regression, not an intended change.
